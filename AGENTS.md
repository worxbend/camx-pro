# Repository Guidelines

## Project Structure & Module Organization

`camx-pro` is a monorepo for a printable pan–tilt camera: CAD, ESP32 firmware and two
remotes. Each project owns its source, tests, configuration and generated output; see
[docs/architecture.md](docs/architecture.md) for dependency rules.

CAMX Pro is standalone. Keep its implementation, tests, configuration and assets
independent of sibling repositories. Do not introduce source imports, symlinks,
build steps or runtime configuration that depend on another checkout. Use
`@camx-pro/*` for local npm packages and `CAMX_PRO_*` for application environment
variables. Third-party libraries use the declared package dependencies; generated
release assets belong to this repository. Define behavior from this project's
contracts and requirements rather than another project's implementation.

- `hardware/`: build123d CAD (`cad/`), mechanical tests and audit tools, engineering docs.
- `firmware/`: PlatformIO project. Portable C++17 in `include/camx/` (motion profile,
  controller, protocol, storage, status), the ESP32 adapter in `src/main.cpp`, the
  embedded panel `web/index.html`, host tests in `tests/`, tools in `tools/`, API and
  verification records in `docs/`.
- `apps/remote/` (Solid.js 2 web remote), `apps/site/` (website and CAD viewer),
  `apps/tui/` (Scala 3 / Glyphora terminal remote with a pinned Mill launcher).
- `packages/control/` (the web remote's session, HTTP transport and demo simulator) and
  `packages/bridge/` (loopback host and ESP32 proxy). npm workspaces with `src/` and `test/`.
- `contracts/state-v1.json`: firmware-generated state fixture read by every client's tests.
- `tests/integration/`: Playwright scenarios against the real C++ controller.

Generated files stay out of Git: `hardware/exports/`, app `dist/`, `apps/tui/out/`,
`firmware/.pio/`, `firmware/include/web_ui.hpp`. `firmware/include/camx/mechanics.hpp` is
generated by `tools/contracts/firmware.py` and committed; never edit or reformat it by hand.

## Build, Test, and Development Commands

Run from the repository root unless noted; `make help` lists the shared targets.

- `make check-contract` — CAD constants match the firmware header.
- `make test-firmware` — native C++ suites with ASan/UBSan (`CXX=g++` selects GCC).
- `pio run -d firmware -e public` and `python firmware/tools/check_variants.py` — ESP32 builds.
- `npm ci`, then `npm test` (Node unit tests), `npm run format:check`,
  `node firmware/tools/test_ui.mjs` (firmware panel in Chromium).
- `npm run assets:fetch && npm run build`, then `npm run test:browser` (integration).
- `cd apps/tui && ./mill app.test` (JDK 25); `./mill app.assembly` and
  `python3 apps/tui/scripts/test_pty.py` and `python3 apps/tui/scripts/test_environment.py`
  for packaged terminal and configuration checks.
- `make setup-hardware`, `make test-hardware`, `make export-hardware` — CAD (uv, Python 3.14).

Use `git status --short`, `git diff` and `git diff --check` before committing.

## Coding Style & Naming Conventions

JavaScript, JSX, JSON, CSS and HTML use the root Prettier configuration (two spaces).
C++ follows `firmware/.clang-format` (LLVM base, four spaces, 100 columns). Scala uses
Scala 3 significant indentation and compiles with `-Wunused:all -Werror`. Use
descriptive names, keep modules focused, match the surrounding code, and avoid
unrelated formatting changes.

## Testing Guidelines

Add tests with every behavior change, next to the project that owns it: firmware tests
are `firmware/tests/*_test.cpp` (discovered automatically), Node tests
`packages/*/test/*.test.mjs`, Scala tests under `apps/tui/app/src/test/`, cross-project
browser tests in `tests/integration/web/`. A change to the firmware state document must
regenerate `contracts/state-v1.json` from `firmware/tests/simulator.cpp` and keep both
remotes working with firmware that lacks the new fields (`api_minor`). Record what was
verified, and what could not be, in the relevant `docs/` or `firmware/docs/` file. No
automated test moves hardware.

## Commit & Pull Request Guidelines

Use concise, imperative commit subjects, such as `Add diagonal jog to the firmware
panel`. Keep commits focused on one project or concern.

Pull requests should explain the change, link related issues when applicable, and record
validation performed or why it could not run. Include screenshots for visible interface
changes.

## Security & Configuration

Never commit credentials, private keys, or local environment secrets. Firmware Wi-Fi
credentials and the API token live in the ignored `firmware/include/credentials.h`
(copy `credentials.example.h`); configured binaries contain them and must stay private.
The bridge binds to loopback only. Provide placeholder configuration examples and add
ignore rules when introducing tools or generated files.
